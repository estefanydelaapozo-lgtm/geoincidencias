# GeoIncidencias — Cambios de esta entrega (30/07/2026)

Todo lo anterior se mantiene: no se tocó Docker, docker-compose, rutas base,
autenticación, ni ninguna funcionalidad existente. Los cambios son
correcciones puntuales + capa visual nueva.

## ⚠️ Importante: no pude ejecutar `docker compose up --build`

Este entorno de trabajo no tiene Docker ni acceso a internet, así que no
pude levantar el stack para probarlo end-to-end. Revisé el código
manualmente con mucho cuidado (balance de llaves/paréntesis, `node --check`
en todo el JS nuevo/editado, lectura completa de cada archivo tocado), pero
**te recomiendo correr `docker compose up --build` y probar el flujo de
aprobar/rechazar/reabrir y el panel del técnico antes de darlo por
definitivo**, sobre todo la migración nueva (`php artisan migrate`).

## Backend (Laravel)

1. **Aprobar ya no exige comentario.** `PUT /incidencias/{id}/aprobar` acepta
   `motivo` opcional. `PUT /incidencias/{id}/rechazar` sigue exigiéndolo
   (mínimo 5 caracteres) y queda visible para el ciudadano, el admin y el
   historial (ya existía ese campo, no se tocó).
2. **Nuevo: reabrir incidencia.** `PUT /incidencias/{id}/reabrir`
   (admin/supervisor, motivo obligatorio) — solo si está Resuelta, En
   verificación o Cerrada. Agrega los estados `En verificación` y
   `Reabierta` vía migración aditiva (no borra ni renombra estados
   existentes).
3. **Nuevo: solicitar revisión.** `POST /incidencias/{id}/solicitar-revision`
   — el ciudadano que reportó la incidencia puede pedir revisión cuando está
   Resuelta o Cerrada; notifica a supervisores/administradores.
4. **Permisos del rol Técnico corregidos** (ya existía como rol
   institucional, pero tenía huecos):
   - Ahora ve **solo las incidencias que le asignaron a él**, no todas las
     de su institución (antes veía las de todos los técnicos de su área).
   - Ahora **puede subir fotos/evidencia** (antes el endpoint se lo
     bloqueaba silenciosamente con 403).
   - Sigue sin poder aprobar, rechazar, eliminar ni reabrir.
5. **Ciudadano:** solo puede editar su incidencia mientras está
   "pendiente de validación" (antes podía editarla en cualquier estado).
6. **Comentarios/seguimiento:** antes cualquier usuario autenticado podía
   ver y comentar cualquier incidencia de cualquier otra persona. Ahora
   solo pueden verlos/comentarlos: el creador, el admin/supervisor, o el
   usuario asignado.
7. **Supervisor ahora puede asignar técnicos** (antes esa ruta era
   exclusiva de admin, contradecía tu lista de permisos del punto 14).
8. **Reportes:** se agregaron porcentajes a resumen, por-categoría,
   por-estado y por-responsable; nuevos endpoints `por-zona` y
   `por-anual`. `por-responsable` ahora también trae el rol, para poder
   separar técnicos de supervisores en el reporte.
9. **Dashboard:** el resumen ahora incluye `rechazadas` y `reabiertas` con
   sus porcentajes, y se cachea 30s (se invalida automáticamente al crear/
   editar/aprobar/rechazar/reabrir una incidencia).
10. Índices existentes ya cubrían las consultas nuevas (no hizo falta
    agregar más).

## Frontend

1. **Rediseño visual completo** (`styles.css` / `styles.min.css`): paleta
   violeta (#6D28D9 / #8B5CF6 / #A78BFA) sobre fondo claro, tipografía
   Plus Jakarta Sans + Inter, tarjetas blancas con sombra suave, sidebar
   claro, botones con gradiente violeta, tablas, badges, formularios,
   login/registro, perfil y panel de negocio — todo recoloreado. Es una
   capa CSS que se agrega al final del archivo (no se borró nada de las
   dos capas anteriores), así que si algo se ve raro en una pantalla que
   no haya revisado a fondo, es cuestión de ajustar esa capa final, no de
   tocar lógica.
2. **Panel de supervisor:** "Aprobar" ahora es un solo clic con
   confirmación, sin pedir motivo. Se agregó el botón "↺ Reabrir" para
   incidencias resueltas/en verificación/cerradas.
3. **Dashboard (`index.html`):** se agregaron las tarjetas de
   "Rechazadas" y "Reabiertas" con porcentaje, además de las 4 que ya
   existían (total, pendientes, en proceso, resueltas).
4. **Panel institucional (`institucion.html`):** era de solo lectura — el
   técnico no tenía ninguna forma de trabajar sus incidencias desde la
   interfaz. Se agregó un botón "Gestionar" por fila que abre un panel
   para cambiar de estado, subir evidencia/foto y agregar observaciones
   técnicas, usando los endpoints que ya existían en el backend.
5. Reportes (`reportes.html`/`reportes.js`) ya tenían gráficos (dona,
   barras, línea), exportación a Excel/PDF y tasas por responsable —no
   se tocó esa parte porque ya cumplía lo pedido; solo se aprovechan los
   nuevos porcentajes que ahora manda el backend.

## Simplificaciones conscientes (por el tamaño del pedido)

- No se construyó un flujo de "aceptar/rechazar asignación" separado para
  el técnico: la aceptación se expresa cambiando el estado a "En proceso",
  que es lo que ya hacía el sistema. Armar un estado de asignación
  pendiente/aceptada aparte habría significado tocar el modelo de datos
  de forma más profunda de lo que el resto del pedido permite sin
  arriesgar romper el flujo ya probado.
- El punto "optimizar con memo/lazy/useMemo/etc." no aplica: el frontend
  es HTML/JS vanilla, no React. Se optimizó lo equivalente en Laravel
  (cache, eager loading, paginación), que ya estaba bastante bien hecho
  de antes.
- No pude ejecutar pruebas de carga, Docker, ni migraciones reales — solo
  revisión estática cuidadosa del código.

## Antes de usarlo

```bash
docker compose up --build
docker exec -it geo_backend_final php artisan migrate --force
```

La migración nueva es aditiva (agrega estados, no borra nada), así que es
segura de correr sobre tu base existente.
